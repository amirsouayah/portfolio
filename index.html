Playwright, IA, RAG et MCP.

L'automatisation des tests change avec l'IA générative. Cette page présente la façon dont j'associe Playwright à des modèles de langage, pour écrire et maintenir les tests plus vite sans perdre le contrôle de la qualité.

PlaywrightTypeScriptRAGMCPCI/CD

Playwright

Le socle : des tests de bout en bout en TypeScript, exécutés à chaque livraison dans la chaîne CI/CD.

Un modèle de langage propose des scénarios et des corrections de sélecteurs. L'ingénieur relit, corrige et valide.

RAG

Le modèle reçoit les spécifications et les tests existants du projet, pour produire des scénarios qui collent au métier.

MCP

Un protocole standard qui relie le modèle aux outils : navigateur, dépôt de code, gestion des tests.

1 · Périmètre des tests

Tests fonctionnels

Objectif
S'assurer que les fonctionnalités spécifiées sont bien présentes.
Importance
Très élevée
Stratégie
  • Identifier les cas de test représentatifs à partir des spécifications et des cas d'utilisation.
  • Écrire le scénario de test avant de coder chaque cas d'utilisation.
  • Dérouler ce scénario une fois le code livré.
  • Faire tester les fonctionnalités par le client.

Inspection de l'interface

Objectif
Une interface de qualité, conforme aux standards.
Importance
Élevée
Stratégie
  • Faire tester et valider l'interface par le client.
  • La comparer aux standards et aux autres outils de l'environnement.
  • Auditer l'accessibilité et le référencement avec Lighthouse, Axe ou Wave.
  • Simuler les parcours utilisateur avec un outil d'automatisation comme Playwright.
1 · Périmètre des tests

Non-régression

Objectif
Stabilité, qualité, fiabilité.
Importance
Très élevée
Stratégie
  • Identifier les fonctionnalités les plus critiques et leurs cas de test.
  • Rejouer ces tests régulièrement, de façon automatisée dès que possible.
  • Ajouter un cas de test pour chaque problème trouvé, afin qu'il ne revienne pas.
1 · Périmètre des tests

Tests unitaires

Objectif
Vérifier que chaque unité de code, fonction ou méthode, produit le résultat attendu.
Importance
Très élevée
Stratégie
  • Chaque classe de l'application a sa classe de test Jest.
  • Le développeur qui écrit une classe écrit son test dans la foulée.
  • Tous les tests rejoignent une suite exécutée en entier à chaque modification.
1 · Périmètre des tests

Tests de performance

Objectif
Vérifier les performances du produit.
Importance
Modérée
Stratégie
  • Identifier ce qui peut dégrader les performances de l'application.
  • Décrire les tests qui répondent aux exigences de performance.
  • Les dérouler tout au long du développement.
  • Outils : Apache JMeter, LoadRunner, Gatling, Locust.

3 · Gestion des tests automatisés

Un seul suivi pour les tests manuels et automatisés

Il faut voir les résultats de tous les tests, quelle que soit la façon dont ils sont exécutés, et connaître à tout moment la couverture des exigences. Chaque test est donc lié à une exigence, et la chaîne d'intégration continue remonte ses résultats. Xray le permet dans Jira :

  1. 1Créer les tests dans Jira
  2. 2Écrire le code de test automatisé
  3. 3Exécuter les tests dans l'environnement CI
  4. 4Rapporter les résultats sur les tests dans Jira

4 · Perspectives et recommandations

Passer au BDD

Le BDD (Behavior Driven Development) part du comportement attendu de l'application, et non de ses fonctionnalités prises une à une.

GherkinLe langage qui décrit les scénarios en phrases lisibles par tous.
CucumberL'outil qui relie chaque phrase du scénario à un test automatisé.
PlaywrightL'outil qui exécute ces tests dans les différents navigateurs.
4 · Perspectives et recommandations

Du besoin à la livraison en sept étapes

  1. Le métier exprime son besoin.
  2. Le Product Owner décrit les comportements attendus.
  3. Le QA rédige les scénarios de test qui valident ces comportements.
  4. Le développeur écrit le code qui répond aux scénarios.
  5. Le développeur ajuste le code jusqu'à ce que les scénarios passent.
  6. Le QA vérifie que les scénarios passent.
  7. La fonctionnalité peut être livrée.
4 · Perspectives et recommandations

Ce que le BDD apporte

Une meilleure communicationMétier, Product Owner, QA et développeurs lisent les mêmes scénarios.
Un développement guidé par l'usageLe code répond au comportement attendu par l'utilisateur.
Une documentation toujours à jourLes scénarios décrivent ce que fait l'application, et ils sont exécutés.
